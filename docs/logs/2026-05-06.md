# Session Log — 2026-05-06

## Summary

Phase 6 security implementation: mutual TLS on the embedded Kestrel gRPC server.
No game logic changes. The shared-secret header check is removed and replaced by
TLS client certificate validation at the transport layer.

---

## What Changed

### `GrpcServerHost.cs` — Full rewrite

Replaced the legacy `Grpc.Core.Server` with an ASP.NET Core `IHost` + Kestrel.
The old implementation used `ServerCredentials.Insecure` with a port binding.
The new implementation uses `UseHttps` with:

- `ServerCertificate` — Unity's own certificate loaded from PEM files via
  `X509Certificate2.CreateFromPemFile`. On Windows, the cert is exported as PFX
  immediately after loading so Kestrel can access the private key.
- `ClientCertificateMode.RequireCertificate` — Kestrel rejects any TLS handshake
  that does not present a client certificate.
- `ClientCertificateValidation` callback — builds a custom `X509Chain` with only
  the project CA in `CustomTrustStore`; revocation check disabled (no CRL endpoint
  in a local PKI).

Signature changed from `Start(int port)` to
`Start(int port, string certPath, string keyPath, string caCertPath)`.

### `IoTGameServer.cs` — Signature update

`Initialize(int grpcPort, string secret)` → `Initialize(int grpcPort, string certPath, string keyPath, string caCertPath)`.

`SharedSecret` property removed entirely — no longer needed since authentication
is handled by the TLS handshake.

### `ServerBootstrap.cs` — CLI args update

Removed `-sharedSecret` parsing. Added:
- `-grpcCert` — path to `unity-server.crt`
- `-grpcKey` — path to `unity-server.key`
- `-caCert` — path to `ca.crt`

Defaults point to `Assets/Certs/` so the server works out-of-the-box when certs
are placed there. Cert paths are forwarded to `IoTGameServer.Initialize()`.

### `IoTGameServiceImpl.cs` — Remove shared secret validation

`ValidateSecret(ServerCallContext)` method removed.
All three RPC methods (`SendInputEvent`, `SendEnvironmentEvent`, `SendInputBatch`)
no longer call it. If the client reaches a service method, its certificate has
already been validated by Kestrel.

### `link.xml` — New stripping exemptions

Added three assemblies to prevent IL2CPP from stripping mTLS internals:
- `System.Security.Cryptography.X509Certificates`
- `System.Security.Cryptography.Pkcs`
- `Microsoft.AspNetCore.Server.Kestrel`

### `Assets/Certs/.gitignore` — New file

`*.key` and `*.crt` are gitignored. `ca.crt` is explicitly un-ignored (safe to
commit — it is a public certificate). Server cert and key must never be committed.

## Architecture Decision: Why mTLS over the existing shared secret

The shared secret was validated in application code after the gRPC connection was
established. Anyone who could reach port 9090 on the Unity host could attempt
connections and probe the service. The secret was also a string in config — one
leak (log file, env var dump, config commit) and the protection was gone.

mTLS pushes authentication to the TLS handshake. An unauthenticated caller cannot
even complete a TCP/TLS connection. The Unity server never sees a gRPC message from
an uncertified peer. The private key never leaves the filesystem, so there is nothing
to leak from a config file.

---

## Known Issue: `Grpc.Core` vs `Grpc.AspNetCore`

The previous `GrpcServerHost` used `Grpc.Core.Server` (legacy C-core binding). The
new version uses ASP.NET Core hosting with `Grpc.AspNetCore.Server`.

- `Grpc.Core.Server` is self-contained — no ASP.NET Core host required.
- `Grpc.AspNetCore.Server` requires `Microsoft.AspNetCore.*` packages.

The `Assets/Plugins/grpc/` folder was set up in Phase 1 for `Grpc.AspNetCore.Server`
(after the initial `Grpc.Core` `grpc_csharp_ext` DLL issue). These DLLs were already
present. If the Kestrel host fails to start, verify the DLL list matches what Phase 4
documented.
